## Category C
My project will contain a .env file with a password. The project may also generate log files and .net build, so these files should never be committed to the repository.

My .gitignore will contain:

.env
*.log
bin/
obj/
.vs/
*.user

The .env file should be ignored because environment files may contain sensitive configuration information such as passwords, API keys, access tokens, database credentials, or other secrets.

Although the .env file in this project will contain only an obviously fake secret for demonstration purposes, excluding it demonstrates the correct practice that should be followed in a real project.

The *.log rule prevents log files from being committed because log files are generated during application execution and may contain temporary or sensitive information.

The bin/ folder should be ignored because it contains compiled .NET application output. These files are generated automatically when the application is built and therefore do not need to be stored in Git.

The obj/ folder should also be ignored because it contains temporary files generated by the .NET build process. These files can be recreated automatically from the source code.

The .vs/ folder contains Visual Studio-specific settings and temporary project information. These files relate to my local development environment and are not required by other developers to build or run the application.

The *.user rule ignores user-specific Visual Studio configuration files because these settings may be different for each developer.

If a real .env file containing a secret were committed and later needed to be removed, simply deleting it in a later commit would not remove it from earlier Git history.

Completely removing the file could require rewriting the repository history. This could change commit hashes and cause problems for teammates whose local repositories still reference the original history. They might need to reset, rebase, or clone the repository again.

A teammate could therefore lose a stable shared history, and existing references to commits could become invalid. This is why sensitive, generated, and developer-specific files should be excluded.

## Approach 1: Merge

A merge combine multiple commits from different branches into a signle unified history.

A merge preserves:
The original commits and their commit hashes.
The point where the branches originally diverged.
That development happened independently on two branches.
It discards nothing about the sequence of events. 

## Approach 2:Rebase then fast-forward 

A rebase is the process of combining a sequence of commits to a new base commit.

A rebase preserves:
The changes introduced by the feature.
The logical purpose of the feature commits.
The order of the feature's work.

It discards the fact that commits wee originally made against older base.
